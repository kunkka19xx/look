Could this be cherry-picked to webkitglib/2.54? It turns out to be user visible, not only an inspector detail.

On WebKitGTK 2.54.0 and 2.54.1 (Skia compositor) every accelerated opacity or transform animation ends with a one frame flash. On the tick where TextureMapperAnimation::apply() flips the state to Stopped it still computes the final keyframe value (the comment there says "we should calculate the last value to avoid a flash"), but reports hasRunningAnimations = false. SkiaCompositingLayer::opacityForAnimationsState(), localTransform() and filter() then ignore that value because isRunning is false and return the static layer property instead, which the main thread last committed when the animation started. For a fade-in that paints the layer nearly transparent for one frame, and the next frame the main thread commits the final style and everything is fine again. TextureMapperLayer kept the last value, so 2.52 does not flash.

Minimal reproduction in a plain GTK window (opaque or RGBA, same result): a div with "animation: arrive 340ms backwards" (opacity 0 to 1, scale 0.965 to 1) containing children with their own 460ms opacity + translate animations, retriggered every 2.2s. A 60 fps screen recording shows two glitch frames per cycle, exactly 340ms and 460ms after the animation starts. A scale-only animation shows no visible glitch, because the stale value is just 3.5% smaller. Source, patch and capture scripts: https://github.com/kunkka19xx/look/tree/experiment/webkit-issue/docs/webkit-254-flicker and https://github.com/kunkka19xx/look/issues/531

320494@main applies to 2.54.1 with a 5 line offset and no conflicts, and fixes it.
